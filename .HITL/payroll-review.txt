# Where I would improve it now

There are several **important gaps**.

They are more serious than visual refinements.

# P0 — Approval policy is not yet fully authoritative

This is the most important issue I found.

Payroll settings currently define:

```text
approverRoles
secondApproverAbove
requireWarningsAcknowledged
blockOnErrors
lockInputsOnApproval
```

and the seed configuration actually enables warning acknowledgement and specifies a second-approver threshold.

But `approveRun()` currently enforces essentially:

```text
correct state
+
same calculation version
+
no blocking/error exceptions
```

It does **not yet appear to enforce** all of the configured approval policy, such as:

* approver role
* second approver threshold
* mandatory warning acknowledgement.

The current approval action and settings therefore risk becoming **two different authorities**.

### Fix this before adding more UI.

Create one authoritative policy:

```text
evaluatePayrollApproval(run, actor, settings)
```

returning something like:

```text
canApprove
requiresSecondApproval
blockingReasons[]
warnings[]
requiredApprovers[]
calculationVersion
```

Both:

```text
ApprovalDialog
```

and:

```text
approveRun()
```

should consume the same policy.

---

# P0 — “Reviewed” is not yet a real payroll state

This is another significant semantic issue.

In the approval dialog, `reviewedBy` is currently inferred from an employee who acknowledged an exception:

```text
run.exceptions.find(e => e.acknowledgedBy)
```

That is not the same thing as:

> “This payroll calculation has been reviewed.”

The workspace also stores:

```text
changedSinceReview
```

as local client state. A browser refresh can therefore lose the concept of what changed since review.

### Add a genuine review record.

For example:

```text
PayrollReview {
  calculationVersion
  reviewedBy
  reviewedAt
  findingsAtReview
  acknowledgedWarnings
  note?
}
```

Then:

```text
CALCULATED
   ↓
REVIEWED
   ↓
APPROVED
```

doesn't necessarily need another visible URL or wizard step—but it needs a **real domain event**.

---

# P0 — Recalculate currently does not really recalculate

This is acceptable for the current demo, but it must not survive into a production backend.

The server action currently advances:

```text
calculationVersion
lastCalculatedAt
updatedAt
```

and returns a count.

The import action likewise accepts validated rows but explicitly acknowledges that there is no input store yet.

Therefore the UI can currently say:

> Calculation #9 complete

without necessarily having generated materially different payslip calculations.

### Production requirement

The real pipeline should be:

```text
input accepted
      ↓
run becomes STALE
      ↓
calculation requested
      ↓
new immutable calculation
      ↓
new payslip results
      ↓
variance generated
      ↓
exceptions generated
      ↓
review invalidated
```

That is a crucial next step.

---

# P0 — Authentication and payroll authority

Right now:

```text
CURRENT_USER_ID = 'emp-020'
```

exists on the server as the Finance head placeholder, because authentication has not landed yet.

For payroll, auth is not merely “login”.

You will need:

```text
Who may see payroll?
Who may see individual compensation?
Who may edit?
Who may recalculate?
Who may acknowledge?
Who may approve?
Who may release funds?
Who may see bank details?
Who may export?
```

### Required model

At minimum:

```text
payroll.view
payroll.process
payroll.review
payroll.approve
payroll.payment.release
payroll.payment.reissue
payroll.settings.manage
payroll.report.export
payroll.audit.view
```

And actions must enforce these server-side.

# P1 — Fix “Employees paid”

There is a small but important semantics issue in the dashboard metrics:

```text
title: 'Employees paid'
```

is derived from `currentRun.employeeCount`, even though the selected run can still be awaiting approval.

For a pending payroll, those people have **not been paid yet**.

Use:

```text
Employees in run
```

or:

```text
Employees
```

Then after settlement:

```text
218 / 218 paid
```

comes from actual settlement state.

Payroll language must be extremely literal.

---

# P1 — Multi-country is only partially prepared

The architecture already anticipates it.

Settings contain:

```text
SG Monthly
MY Monthly
```

with different currencies and entities.

But the active calculation seed is explicitly:

```text
CURRENCY = SGD
CPF employee = 20%
CPF employer = 17%
Tax = 15%
SG Monthly
```

And the Payroll dashboard itself currently contains:

```text
const CURRENCY_SYMBOL = 'S$'
```

### Remove presentation-level country assumptions now.

Even before Malaysia payroll is implemented, the frontend should always derive:

```text
currency
country
entity
timezone
rule pack
```

from the selected run/pay group.

Never:

```ts
const CURRENCY_SYMBOL = 'S$'
```

inside a generic payroll dashboard.

# P1 — Add a run-level Input Readiness surface

The employee inspector has an excellent Inputs view.

But at **run level**, I would still add:

```text
INPUT READINESS

Compensation       Ready
Attendance         Ready
Overtime           3 pending
Leave              Ready
Commission         Ready
Adjustments        4 imported
```

This could be a Sheet opened from the **Inputs** lifecycle stage.

It should answer:

> Are all upstream inputs ready before calculation?

The current lifecycle bar tells you where the run is, but not whether the underlying feeds are complete.

# P1 — Make “stale calculation” impossible to miss

When inputs are imported after a calculation, show a persistent state such as:

```text
CALCULATION OUT OF DATE

17 payroll inputs changed after calculation #8.

Recalculate payroll →
```

Do not rely on a toast.

Then Approval should be unavailable until the new calculation exists.

This is one of the most important payroll trust patterns.

---

# P1 — Persist change sets

Today `changedSinceReview` is a client number.

Instead create:

```text
CalculationDiff
```

with:

```text
previousCalculationVersion
currentCalculationVersion

affectedEmployees
grossDelta
netDelta
employerCostDelta

componentChanges[]
inputChanges[]
exceptionsAdded[]
exceptionsResolved[]
```

Then approval can say:

```text
Changes since review

12 employees affected
Gross +RM18,420
Net +RM13,170

8 overtime changes
3 salary changes
1 tax change
```

This becomes extremely powerful.

---

# P1 — Improve bulk selection semantics

Current checkbox semantics explicitly select the current page.

For larger payrolls, add the familiar pattern:

```text
25 employees selected.

Select all 218 employees matching these filters
```

This matters when bulk recalculating or exporting.

---

# P2 — Scale the table only when necessary

The current client-side table is absolutely fine for the present dataset.

Do **not** prematurely introduce AG Grid or an enormous grid architecture.

But establish a threshold:

```text
< 1,000 employees
TanStack client sorting/filtering/pagination

1,000–5,000
consider server pagination/filtering

5,000+
server data model + virtualization
```

The current route loads all rows and history server-side, and employee history is constructed by iterating earlier runs and fetching each run's payslips.

The comments already acknowledge this should become one database query later.

Correct.

---

# P2 — Optimistic mutation concurrency

The current client mutation helper takes a snapshot of `run`, applies an optimistic update, and restores that snapshot if the action fails.

For a demo, excellent.

With a real backend, overlapping mutations could eventually produce stale rollback problems.

When live data arrives, move to either:

```text
serialized mutations
```

or:

```text
server-authoritative query cache
```

with optimistic patches keyed to individual records.

Do not rebuild this prematurely.

# UI/UX philosophy I recommend

The code is now mature enough that Payroll should have its own **product philosophy**, not its own design system.

## 1. Payroll is a control room, not a dashboard

Every important surface should answer:

```text
What needs attention?
What changed?
What happens next?
```

---

## 2. Exceptions, not exhaustive checking

The system should progressively move toward:

> **Humans review exceptions. The system proves the ordinary cases.**

---

## 3. Every number must be explainable

For every material payroll value:

```text
Value
 ↓
Composition
 ↓
Source
 ↓
Rule
 ↓
Calculation
 ↓
Approval
 ↓
Settlement
```

Your inspector architecture is already heading there.

---

## 4. Context preservation over navigation

Keep:

```text
Table ↔ Inspector
```

Keep:

```text
Sheet for exceptions
```

Keep:

```text
Dialog for approval
```

Avoid route changes for minor inspection.

---

## 5. Consequence-aware actions

Never:

```text
Approve
```

Prefer:

```text
Approve calculation #9
218 employees
RM481,244 net payroll
0 blockers
```

Your current approval dialog already does this very well.

---

## 6. State must be truthful

Never say:

```text
Paid
Reviewed
Calculated
Ready
```

unless the domain has evidence that it occurred.

This should become a very strict Payroll UX rule.

---

## 7. Quiet UI, strong exceptions

Normal payroll should be visually calm.

```text
normal
normal
normal
normal
⚠ anomaly
normal
```

rather than:

```text
blue
green
orange
purple
yellow
red
```

Your current AdminCN-based implementation is already well positioned for this.

# Final assessment

I would classify the build as:

> ## **A very strong Payroll UX prototype / frontend reference implementation that is now approaching the point where additional UI work yields less value than making its states authoritative.**

The most impressive aspect is that it has **not become a collection of Shadcn pages**.

It has a coherent payroll product model:

```text
Dashboard
     ↓
Run
     ↓
Exception
     ↓
Employee
     ↓
Explanation
     ↓
Reconciliation
     ↓
Approval
     ↓
Payment
     ↓
Compliance / Audit
```

That is the right architecture.

The next evolution should therefore be:

> **from beautiful payroll simulation → trustworthy payroll operations system.**

And I would establish one overriding requirement for every subsequent feature:

> ### **Never display a payroll state that the domain cannot prove.**

That single philosophy will improve the UI, UX, backend architecture, auditability, approval model and payment design simultaneously.
