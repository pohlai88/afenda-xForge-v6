# 1. Objective

Build Afenda's single canonical **business table interaction engine**.

This is NOT a generic styling wrapper around `<Table>`.

It is the application-level authority for how business data tables operate.

The existing shadcn/Base UI `Table` remains the visual primitive.

TanStack Table remains the computational table foundation unless repository inspection reveals a concrete reason otherwise.

No second table library.

# 6. Column semantics

Columns MUST explicitly declare meaningful capabilities.

Do not infer business meaning from JavaScript type alone.

At minimum investigate a small semantic vocabulary such as:

```text
identity
identifier
text
money
quantity
percentage
date
datetime
status
boolean
relation
```

The final vocabulary must come from actual repository needs.

Sorting/filtering/grouping/aggregation are enabled only when semantically valid.

Examples:

```text
employeeNumber
→ identifier
→ sortable
→ text filter
→ NOT aggregatable

grossPay
→ money
→ sortable
→ numeric filter
→ sum MAY be meaningful

department
→ relation
→ filterable
→ grouping MAY be meaningful
```

No invalid aggregation may be offered.

# 7. Capability rule

A control renders only when the dataset definition supports a meaningful operation.

Examples:

```text
no filters
→ no Filters control

no bulk actions
→ no selection column

no hideable columns
→ no Columns menu

no export
→ no Export action

no row commands
→ no context command affordance
```

Do not render disabled placeholder capability.

# 8. Contextual commands

Object rows with commands use the same domain command descriptors for:

```text

Shift+F10
⋮ / touch equivalent
```

No duplicated command arrays.

Properties remains last.

CRUD-SAP ordering remains canonical.

The table engine renders commands but does not decide domain permissions or business actions.

# 9. Active table scope

This is a critical Phase 02 invariant discovered from the Payroll workspace.

The same workspace may keep multiple table instances mounted while only one is visible.

Therefore:

> A mounted but inactive table MUST NOT participate in keyboard navigation, focus, selection targeting, context-menu targeting, shortcut resolution, or active-object publication.

Every table instance owns its own interaction scope.

Do NOT perform document-global row discovery.

Do NOT infer active status from viewport width or global selectors.

Prefer explicit active/inactive input from the workspace owner.

Record how this works in the engine contract.

# 10. Keyboard model

Do not turn all tables into ARIA grids in this phase.

Preserve semantic HTML table behavior unless a real editable-grid requirement exists.

Do not make every `<tr>` tabbable.

Use the row's canonical object identity control as the Phase 02 keyboard object target where appropriate.

Canonical commands:

```text

Shift+F10
→ Context menu

Alt+Enter
```

Sorting headers and selection controls remain normally keyboard accessible.

Do NOT implement global ArrowUp/ArrowDown row navigation without a separately validated accessible model.

# 19. Responsive behavior

If a task requires a fundamentally different compact surface, that is a separate task-adaptive view, not a responsive mutation of table semantics.

# 28. Contextual menu focus ownership (added after Phase 01 closure)

> **Contextual menu focus handoff SHOULD be lifecycle-driven by the mounted menu content rather
> than frame polling. The trigger owns invocation detection; the mounted menu owns initial focus;
> the table engine owns object focus scope and restoration target.**

```text
Object focus anchor
        ↓
ContextMenu Trigger      detects Shift+F10 / ContextMenu key
        ↓
Popup mounts
        ↓
Popup content            moves focus into the menu
        ↓
Escape / close
        ↓
Table instance           restores original object focus
```

Phase 01 shipped a frame-polling approximation in `ObjectCommands.tsx` `onOpenChange`: a bounded
`requestAnimationFrame` retry, because the popup mounts into a portal after the callback runs and
Base UI's `Menu.Popup` exposes `finalFocus` but no `initialFocus`. It is keyboard-only and does not
touch the pointer path. Replace it here — the content owning its own initial focus is the correct
structure, and this is the phase where the engine owns focus scope and the restoration target.

## Built

- `src/types/common/table-types.ts` — the §5 definition contract and §6 semantic vocabulary.
  Ten semantics drawn from columns this repo actually has. `COLUMN_SEMANTICS` fixes what each
  permits; a column narrows, never widens. Only `money` and `quantity` aggregate, so no surface can
  offer to total a percentage. `deriveTableCapabilities` implements §7: a control exists because the
  definition earns it.
- `src/components/shared/DataTable.tsx` — the engine. Zero domain branches.

## Two boundary decisions

Both were resolved to *remove* domain code rather than add an escape hatch, because a
`rowProps`/`className` hook is exactly the leak §26 tests for.

- **Row emphasis** is `getRowState → 'default' | 'emphasis'`, a domain statement, not a class name.
  The engine decides what emphasis looks like, so it means the same thing in every table.
- **Row click** is owned by the engine and resolves to the object's first `read` command. Both
  pilots hand-roll this today (`router.push(hrefFor(row))`, `onSelectEmployee(id)`); after migration
  neither needs to. The control guard moves into the engine with it, so no table can reintroduce the
  bug where clicking ⋮ navigated the row out from under the menu.

Aggregation is deliberately NOT auto-derived yet: the run queue's footer prints "—" when rows span
currencies, and a generic sum would silently reintroduce cross-currency totalling that an earlier
commit removed. `footer` stays caller-supplied until aggregation can carry currency truth.

## Adopted: faceted options and counts

`payroll-table-toolbar.tsx` has a component named `FacetFilter` that was faceted in name only. Its
options came from the static vocabularies — every payroll status, every payment status, every
department in the company — while `getFacetedRowModel` and `getFacetedUniqueValues` were registered
on the table and their results discarded.

That is a `domain_truth` (D14) problem, not a cosmetic one: offering "Blocked" when no employee on
the run is blocked implies a blocked employee sitting behind the filter. Options now come from
values rows actually carry, with counts, and a facet with nothing behind it disappears.

Applied to Status, Payment, Department and Location. **Not** to Exceptions: that column's accessor
is `openBlockers * 100 + openWarnings`, a derived number, so its facet keys can never equal its
option values — counting it would have silently emptied the filter. Hence `faceted` is opt-in per
facet rather than global. Both the five-trigger and collapsed single-Popover paths read the same
derivation, so they cannot disagree.

## Engine implication

The Phase 02 contract already encodes exactly which columns this is valid for. `filter: 'set'` —
`status` and `relation` — means the column's own values *are* the filter values, which is the
precondition for trustworthy facet counts. `money`/`quantity`/`percentage` filter numerically and a
derived accessor cannot be faceted at all. When the toolbar moves into the engine, `faceted` should
be derived from the semantic rather than hand-set, and the hand-set flags here removed.

Faceted min/max stays unadopted: no product table offers a numeric range filter today, and adding
one because TanStack supports it is the chrome §7 forbids.

# Engine upgraded to the full feature envelope

Benchmark: the Studio DataTable catalogue. Foundation: TanStack 8.21.3 (unchanged). UI: existing

## The gating model — support is not chrome

`deriveTableCapabilities` runs three gates in order, and it is the only place chrome is decided:

```
meaningful   does the data make it possible?   columns, selection, export, mode
     ↓
permitted    may this user do it?              TablePermissions; omitted = permitted
     ↓
asked        does the task call for it?        definition.task narrows without removing ability
```

A capability that fails any gate renders nothing — not a disabled control. Permissions gate chrome
only, never truth: a user who may not export still sees every row they are entitled to.

## First-class, implemented

| Capability | How it is gated |
| --- | --- |
| Sorting | any column semantic that sorts; `aria-sort` on every sortable header |
| Filtering (column + faceted multi-select) | any column whose semantic filters |
| Global search | only columns whose semantic is `searchable` — money and dates are excluded, since free-texting a currency is nonsense |
| Pagination | caller-owned state; suppressed for `infinite` mode |
| Selection | present only when `selection.bulkActions` exists |
| Bulk operations | actions resolved *per selection*, so a domain can withhold one these rows do not qualify for |
| Row actions | `getCommands`; context menu + ⋮ + Properties from Phase 01 |
| Column visibility | only columns marked `hideable` |
| Export | `onExport`; exports the filtered set, not the page |
| Loading | skeleton rows holding table height, `aria-busy` |
| Empty state | domain's own words; offers Clear only when a filter caused it |
| Responsive | horizontal scroll with sticky pinned columns |
| Accessibility | `aria-sort`, sr-only `<caption>`, labelled select-all and per-row checkboxes naming the object |

## Architecturally supported, deliberately unrendered

`TableDataMode` (`client` / `manual` / `infinite` / `virtual`), `TableGrouping`, `TableExpansion`,
and `aggregate` all exist in the contract and are reported by `deriveTableCapabilities`. None
renders anything: no Afenda dataset requires them, and building them now would be the chrome §7
forbids. The seam means the first dataset that needs one extends the engine rather than inventing a
second table.

Aggregation stays unrendered for a stronger reason than "not needed": the run queue's footer prints
"—" across mixed currencies, and a generic `sum` over money columns would silently restore the
cross-currency totalling commit 649b505 removed. `footer` remains caller-supplied until aggregation
can carry currency truth.

## Faceting is now derived, not declared

`isFacetable` = the column's semantic filters as a `set` — that is exactly the condition under
which a column's own values are also its filter values, so TanStack's counts line up. A derived
accessor (payroll's `openBlockers * 100 + openWarnings`) is not `set` and is never faceted, which
is the bug the hand-set flag in `payroll-table-toolbar.tsx` had to dodge manually. When the pilots
migrate, those flags disappear.

# Contract frozen + Pilot A migrated

## The two invariants (contract now frozen; no capabilities added)

1. **Export truth respects data-source ownership.** `onExport(rows, scope)` where
   `scope: 'all' | 'loaded'`, derived by `exportScopeOf(mode)`. In `client` mode the engine holds
   every row, so a filtered export is genuinely `all`. Under `manual`/`infinite`/`virtual` the
   source holds the rest, so the same call is `loaded` and the domain decides whether to export
   what is loaded or fetch the remainder. Without it an export produces a partial file that looks
   complete — the worst possible failure for a payroll register.
2. **`TablePermissions` is presentation gating, not authorization.** Stated as an INVARIANT on the
   type: hiding a control is not enforcement, anything reachable from the client is reachable
   without the control, and the domain and server stay responsible for refusing. `false` means
   "do not offer", never "cannot happen".

## Did Pilot A require engine modification? YES — two, both mechanics, neither a domain branch

1. **Sortable header rendering.** Sorting is declared first-class but the engine only emitted
   `aria-sort`; the run queue rendered its own toggle with chevrons and Enter/Space handling. The
   engine now owns it, driven by `capabilities.sort` and labelled from the declared column label
   (`aria-label="Sort by Run"`).
2. **Numeric alignment from semantics.** The view carried `RIGHT_ALIGNED = new Set([...column ids])`.
   The engine derives it from `money | quantity | percentage`, so alignment is decided by meaning
   once instead of by a per-table list. That set is deleted.

Both are engine-owned mechanics read from the contract. No `rowProps`, `className`, `renderRow`
hatch was added, and grep confirms no payroll vocabulary in the engine files.

## Bug found by migrating

Moving the empty message from lazily-rendered JSX into an eagerly-built definition object exposed
`RUN_LIFECYCLE_LABELS['all']` → `undefined.toLowerCase()`, crashing the page on every render. The
original only evaluated inside the empty branch, so the same latent bug would have fired the first
time a filter-free queue came back empty. Now guarded, with an honest 'No runs yet.' for that case.
