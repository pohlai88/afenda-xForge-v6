# 4. Establish a canonical Object Context contract

Afenda needs a consistent way for UI surfaces to describe:

> What object is the user interacting with?

Do NOT create an enterprise-wide domain entity abstraction.

Create only the minimum UI interaction contract required for contextual commands.

Conceptually investigate something equivalent to:

```ts
type ObjectContext = {
  type: string
  id: string
  label: string
  href?: string
}
```

Do NOT blindly use this exact API.

Derive the smallest contract from actual repository needs.

It MUST:

* identify the object type;
* identify the object instance;
* provide a human-readable label;
* allow commands to resolve against it.

It MUST NOT:

* duplicate the domain model;
* become a second entity registry;
* contain business data;
* contain permissions;
* contain arbitrary metadata bags merely for future flexibility.

Permissions and actions remain owned by domains.

---

# 5. Context menu becomes the universal contextual entrance

Use the existing shadcn/Base UI `ContextMenu` primitive if available.

Do not create another visual primitive.

Establish one reusable **contextual command composition pattern**.

The semantic rule is:

```text
RIGHT CLICK
=
WHAT CAN I DO WITH THIS OBJECT?
```

Supported invocation MUST eventually map to:

```text
Right click
Shift+F10
Touch/overflow equivalent
```

For Phase 01, mouse + keyboard support are required where the primitive permits.

---

# 6. Stable context-menu grammar

Context menus should follow this ordering where commands exist:

```text
DEFAULT
Open

WORKSPACE
Open to side        [future capability; omit until implemented]
Compare...          [omit unless real]

OBJECT ACTIONS
domain-specific commands

OUTPUT
Copy reference
Export              [only where meaningful]

AUDIT / SOURCE
History
Audit
Source              [only where real]

SYSTEM
Properties
```

Important:

**Do not render menu groups merely because the grammar defines them.**

If the object does not support a command:

```text
omit it
```

Do not show meaningless disabled commands.

`Properties` should remain last where present.

---

# 7. Implement Properties as a semantic contract

Doctrine definition:

```text
Properties
=
"What exactly is this object?"
```

Properties MUST NOT automatically mean Edit.

For Phase 01:

Create a canonical presentation pattern using existing primitives.

Prefer:

```text
right-side inspector / Sheet
```

for normal business records.

Do not build workbench groups yet.

Properties content remains supplied by the domain.

The shared infrastructure may own:

```text
header
object identity
section presentation
close behavior
accessibility
```

It MUST NOT own:

```text
employee fields
payroll fields
invoice fields
company fields
```

# 8. Pilot on exactly TWO object types

Do not roll this across the application yet.

Use two substantially different existing objects to validate the grammar.

Recommended candidates:

```text

Employee within Payroll
```

because Payroll is already the reference-quality frontend.

However, inspect the code first and choose different objects if they provide a cleaner proof.

For each pilot object:

### Right click

Should expose only genuine commands.

At minimum investigate:

```text

```

Do not invent unavailable actions.

### Properties

Must expose canonical read-oriented information.

Example categories may include:

```text

```

but use actual domain data only.

# 9. Make summary surfaces query-aware only where trivial

Do not implement Afenda 360 Query yet.

# 11. Breadcrumb is mandatory

Establish the breadcrumb pattern as part of the primary workspace grammar.

Do not invent different breadcrumb implementations per domain.

Use the existing primitive/pattern.

Breadcrumb semantics remain constant across responsive layouts.

Do not convert breadcrumb into:

```text
pagination
tabs
select
```

at narrow widths.

Visual compression is allowed.

Semantic replacement is not.
