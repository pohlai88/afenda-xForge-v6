# 6. Core behaviour

For the currently active/focused first-class business object:

```text
Alt+Enter
```

should open the same Properties experience available through:

```text
right-click
→ Properties
```

There must be one Properties capability.

Do not create:

```text
KeyboardProperties
ShortcutPropertiesSheet
PayrollPropertiesShortcut
```

or equivalent parallel implementations.

The keyboard path must invoke the same underlying shared command/state transition as the pointer path wherever the current architecture permits.

---

# 7. Eligibility law

Alt+Enter must operate only when there is a meaningful current business object whose existing command model supports Properties.

Conceptually:

```text
current object exists
AND
Properties is valid for that object
→ Alt+Enter opens Properties
```

Otherwise:

```text
no-op
```

Do not fabricate Properties for objects that do not expose it.

Do not make Alt+Enter itself a new source of capability truth.

The same capability authority used by existing contextual commands should decide.

---

# 8. No object-type branching

Do NOT implement:

```text
if entity_payroll → ...
if payroll_run → ...
if settlement → ...
```

The solution must be object-type agnostic.

Adding a new first-class object later should inherit Alt+Enter automatically when it participates in the existing Properties architecture.

# 9. Shortcut ownership

Find the lowest correct shared layer that knows:

```text
the current object
whether Properties applies
how to open Properties
```

Do not attach independent `keydown` listeners to every page or every business object.

Prefer an existing shell/object interaction boundary.

One shared listener/command mechanism is preferable to page-level listeners.

However:

Do not centralize unrelated keyboard behaviour merely because Phase 09 touches one shortcut.

Keep the phase narrow.

---

# 10. Keyboard event law

The implementation must correctly distinguish:

```text
Alt+Enter
```

from:

```text
Enter
Shift+Enter
Ctrl+Enter
Meta+Enter
Alt+other key
```

Do not accidentally fire Properties for another combination.

Use the actual browser event model in this repository.

Do not infer shortcut identity from printable character output.

---

# 11. Editing/input safety

Alt+Enter must not unexpectedly hijack an interaction where the user is actively editing text or operating a control with an established Alt+Enter meaning.

Inspect existing application conventions.

At minimum evaluate event targets such as:

```text
input
textarea
contenteditable
select
combobox
query filter
dialog fields
```

Do not blindly suppress every Alt+Enter globally.

Define and document the correct boundary.

If the application's existing shortcut infrastructure already has an editable-target guard, reuse it.

---

# 12. Browser/default behaviour

Use `preventDefault()` only when Afenda actually consumes the shortcut.

Do not suppress Alt+Enter globally when:

```text
there is no active object
Properties is unavailable
the event is intentionally excluded
```

Avoid unnecessary propagation interference.

If an existing keyboard dispatcher defines propagation law, follow it.
