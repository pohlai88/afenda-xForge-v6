Yes. Referring back to the **normative Afenda UX doctrine**, I would compose Payroll differently from a conventional HR/payroll menu tree.

The doctrine says Afenda is **“find + operate + understand”**, important entities must be **first-class business objects**, work should preserve context, commands follow **CRUD-SAP**, capability should exist without excessive chrome, there should be **one table interaction engine**, and new routes require proof that they represent genuinely independent work contexts.

That gives us a much stronger payroll architecture.

# Afenda Payroll Product Doctrine

> **Payroll is not a collection of pages.**
>
> It is a connected operating system around a small number of business objects:
>
> **Worker → Employment → Compensation → Payroll Inputs → Payroll Run → Payslip → Payment → Filing → Accounting**

The existing run workspace already follows a lot of this doctrine well: lifecycle, metrics, employee table, drill-down, exceptions, reconciliation and audit are all kept inside one working context rather than fragmented across many pages.

The missing work should therefore extend this model rather than create dozens of new routes.

# Recommended Essential Route Budget

I would formalize the Payroll domain as only **eight primary workspaces**:

| Route                 | Purpose                        |
| --------------------- | ------------------------------ |
| `/payroll`            | Control Center                 |
| `/payroll/people`     | Payroll population             |
| `/payroll/inputs`     | Inputs and readiness           |
| `/payroll/runs`       | Payroll execution              |
| `/payroll/payments`   | Payment execution              |
| `/payroll/compliance` | Statutory obligations          |
| `/payroll/reports`    | Reporting and analysis         |
| `/payroll/setup`      | Configuration + implementation |

Everything else is:

**tab · inspector · sheet · dialog · drill-down · properties · context command**

unless it genuinely deserves its own independently addressable object workspace.

That is much closer to Afenda's doctrine.

# The Common Afenda Object Pattern

This is the most important part.

Every significant object should behave consistently.

```text
OBJECT
│
├─ Identity
├─ State
├─ Relationships
├─ Commands
├─ Source
├─ History
├─ Audit
└─ Prediction
```

So:

### Employee

**Open · Change · Search Related · Audit · Predict**

### Compensation

**Open · Change · Correct · History · Source · Predict impact**

### Payroll Input

**Open · Correct · Reverse · Source · Audit**

### Payroll Run

**Open · Calculate · Review · Approve · Audit · Predict**

### Payment

**Open · Release · Reissue · Reconcile · Audit**

### Filing

**Open · Prepare · Submit · Amend · Audit**

This is much more powerful than independently designing each screen.

